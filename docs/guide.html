1 · The Big Picture

What it is. You play a lone survivor in a bounded arena. Enemies spawn at the edge of the screen and walk toward you. Weapons fire by themselves — your only job is to move (WASD / arrow keys). Kills drop XP gems; leveling up pauses the game and offers a 3-card upgrade draft. Waves escalate for 10 minutes, then the Hive Tyrant boss spawns. Kill it and you win.

The end goal — two targets in one project:

  1. A finished, shipped game. Live on itch.io in the browser plus packaged Electron builds for all three desktop OSes.
  2. A computer-graphics techniques showcase. The renderer, collision, and memory management are deliberately built from scratch on WebGL2 so the classic CG topics — instancing, texture atlases, spatial partitioning, post-processing, fixed-timestep simulation — are all visible in the code and measurable in a benchmark.
The one-sentence pitch for the demo: "It's a Vampire Survivors clone where we wrote the renderer ourselves — one draw call draws ten thousand sprites, and we have the benchmark proving why that matters."

2 · Architecture — three clean layers

main.ts sits above all three — it reads game state and pushes sprites into the renderer.

The dependency rule

  • src/engine/ — GPU, clock, grid, keyboard. Cannot import from game/.
  • src/game/ — enemies, weapons, XP, waves. Knows nothing about WebGL calls.
  • src/main.ts — the only file that knows both: it turns world state into renderer.push() calls and runs the menu state machine.
  • src/data/ — pure JSON. Changing game content never requires touching code.
Why it matters: this separation is what lets each team member own a whole layer, and it's why content (enemies/weapons/waves) can be balanced by editing JSON with zero risk of breaking the engine.

3 · Anatomy of one frame

The game renders once per requestAnimationFrame but simulates at a fixed 120 Hz. Slow frames simply run more sim ticks; fast frames may run none.

Sim ticks (green box) repeat 0..N times per rendered frame. Drawing happens once.

What the world does in one tick (120× per second)

1. Spawns Current wave's interval timer; boss trigger at 10:00 updateSpawns
2. Move enemies Seek player + knockback decay + hit-flash decay moveEnemies

5. Separation Push overlapping enemies apart so the horde doesn't stack separateEnemies
6. Weapons Cooldown timers → fire projectiles / nova / aura tick / orbit orbs updateWeapons

4 · Game state machine

main.ts owns one string variable, state, that decides what the update/render callbacks are allowed to do. menu.ts draws the DOM overlay for each non-playing state.

"draft" is interrupt-driven: world.pendingLevels > 0 after any tick re-opens it.

Run lifecycle in prose

  1. menu → Play → weaponselect → pick starting weapon → playing
  2. During play, any level-up sets pendingLevels; the update callback notices and opens draft (one card pick per pending level — chains if you leveled twice in one tick)
  3. ESC toggles paused; pause shows live run stats
  4. hp ≤ 0 → gameover with kills/DPS/level/build summary
  5. Boss killed → victory with the same stats

5 · CG technique — instanced rendering

The problem. GPUs are fast; telling them what to draw is slow. Every drawArrays call costs CPU-side driver work — state validation, command encoding. Ten thousand sprites drawn one at a time means 10,000 draw calls per frame, and the frame rate collapses no matter how good the GPU is.

The fix. WebGL2 instancing draws the same quad N times in one call. Per-sprite data (position, size, color, UV rect, hit-flash, rotation) is packed into a flat Float32Array — 14 floats per sprite — uploaded once, and read in the vertex shader via attributes marked vertexAttribDivisor(loc, 1) ("advance once per instance, not per vertex").

Same vertex shader either way — the difference is how many times the CPU has to call it.

The vertex shader does the camera + rotation

vec2 corner  = aCorner * aSize;                    // unit quad → sprite size
vec2 rotated = rotate(corner, aRot);               // per-instance rotation
vec2 world   = aPos + rotated;                     // world position
vec2 screen  = (world - uCamera) * uZoom / uResolution * 2.0;
gl_Position  = vec4(screen.x, -screen.y, 0, 1);    // world → clip space
"We batch all sprites into one instanced draw call. Per-instance attributes — position, size, color, UV, flash and rotation — advance once per instance via attribute divisors, so a single drawArraysInstanced call renders the whole scene. CPU overhead per frame becomes one buffer upload and one draw call instead of thousands."

Code: renderer.ts — push() writes into the Float32Array, flush() uploads once and draws. The buffer doubles in capacity when full.

6 · CG technique — texture atlas

The problem. Every bindTexture is a GPU state change. Drawing 16 enemy types from 16 separate textures would force re-binds (and break batching).

The fix. All art lives in one 4096×2048 atlas texture, built at runtime on a 2D canvas: procedural shapes + a monospace digit font are drawn in a reserved 512×512 block, and AI-generated 256×256 PNGs are painted into the remaining tile slots as they load. Each sprite instance carries a normalized UV rectangle so one bound texture serves everything.

Nice details worth mentioning

  • Progressive enhancement: if a PNG is missing or still loading, the entity renders as its procedural fallback shape — the game can never break from a missing asset.
  • Walk animation for free: each enemy has a -walk2 tile; the render loop alternates frames at 6 fps offset by enemy id — no animation system needed.
  • Digits in the atlas: damage numbers are just sprites — UV.digit(n) maps a number to its glyph rect, so floating text costs one instanced quad per digit.
  • 2px inset on each tile's UV prevents bleeding between neighbors under linear filtering.
  • Per-instance tint: the same white art tints to any color — gems flash rarity colors, enemies flash white on hit via vFlash mixed in the fragment shader.
"All sprites sample one atlas texture, so the whole scene draws with a single bound texture and zero state changes. Per-instance UV rectangles select which tile each quad shows; tint and hit-flash are done per-instance in the fragment shader."

7 · CG technique — spatial hashing

The problem. Collision checks are pairwise: "is enemy A touching enemy B?" For N entities that's N²/2 comparisons — at 5,000 enemies, 12.5 million distance checks per tick, at 120 ticks per second. Impossible.

The fix. Bucket every entity into a uniform grid of 96px cells (SpatialHash maps floor(x/96), floor(y/96) → array). To find an entity's neighbors you only look in the cells its query circle overlaps — a handful of candidates instead of the whole population. Rebuilt from scratch each tick (cheap: one pass over the array).

Where it's used

  • Enemy separation — each enemy pushes apart neighbors from its own cells
  • Player contact — one query around the player instead of scanning everyone
  • Aura / orbit / projectile hits — each hazard queries only its overlap cells

The query radius is padded by the largest enemy size (derived from enemies.json at construction), so a huge boss can never hide in an unchecked cell.

"Pairwise collision is O(n²), which dies at a few thousand enemies. We bucket entities into a uniform spatial hash each tick, so every query only inspects the handful of cells its circle overlaps — effectively O(n) and it's why the benchmark scales to 10,000 enemies."

8 · CG technique — object pooling & fixed timestep

Object pooling — near-zero garbage collection

At 120 ticks/second a busy game would allocate thousands of short-lived objects per second → frequent GC pauses → visible stutter. Instead, dead entities are pushed onto a freelist and re-initialized on the next spawn: 

// spawn
const e = this.enemyPool.pop() ?? ({} as Enemy);   // reuse or create once
// kill — swap-pop removal keeps the array dense, no splice
es[i] = es[es.length - 1]; es.pop(); this.enemyPool.push(e);
  • Pooled: enemies, projectiles, gems, particles, damage numbers
  • Particles capped at 2,048 · damage numbers at 128 · dying-corpse sprites at 64 — hard caps mean memory and frame cost stay bounded in the worst case
  • Spatial-hash buckets are cleared in place (length = 0), not reallocated

Fixed timestep — same game on every machine

// loop.ts — accumulator pattern
acc += elapsed;                       // real time since last frame (≤250ms)
while (acc ≥ STEP) { update(STEP); acc -= STEP; }   // STEP = 1/120s
render();                             // once, at whatever rate the display wants
Why not update per frame? At 60fps a frame is 16.7ms; at 144fps it's 6.9ms. If physics ran per-frame, gameplay speed would depend on your monitor — and a 30fps laptop would literally play slower.
The 250ms clamp is the "spiral of death" guard: after a long hitch (tab switch), we catch up at most 30 ticks instead of simulating forever and never rendering again.
"Two classic problems, two classic fixes: pooling plus swap-pop removal keeps the hot loop allocation-free so the GC never hitches mid-fight; a fixed-timestep accumulator decouples simulation rate from render rate, so gameplay is identical on every display."

Game-feel extras (cheap tricks, big effect)

  • Hit-stop: killing a high-XP enemy freezes the sim ~60ms — the hit feels heavy
  • Screen shake: camera offset ∝ shake² — decays smoothly, spikes on player damage/boss
  • Hit-flash: per-instance flash lerps the sprite toward white in-shader
  • Knockback: contact adds a decaying velocity vector (kx, ky) on top of seek movement
  • Squash: enemies subtly pulse (w = size·pulse, h = size·(2−pulse)) so the horde feels alive

9 · CG technique — bloom post-processing

The scene isn't drawn to the screen directly — it's rendered into a framebuffer object (FBO, an offscreen texture). Post-processing then treats that image as input to further passes.

Five fullscreen passes: scene, bright, blur H+V (×2), composite.

Why it's cheap

  • Separable Gaussian: a 2D blur kernel factors into horizontal + vertical 1D passes — 2×5 taps instead of 25 per pixel.
  • Half resolution: blur runs at ¼ the pixels; low-frequency glow doesn't need full res anyway.
  • Ping-pong FBOs: two half-res targets alternate as source/destination — the classic trick for iterative blur without allocating more textures. 
// blur fragment shader — 5-tap gaussian weights
sum = tex(uv)·0.227 + tex(uv±dir·1.384)·0.316 + tex(uv±dir·3.230)·0.070;
"Bloom is a three-stage post pipeline over framebuffer objects: threshold the scene for bright pixels, blur them with a separable Gaussian at half resolution using ping-pong FBOs, then additively composite the glow back over the scene."

Fallback: if post-program compilation fails the renderer silently disables bloom — the game still runs everywhere. Naive mode disables it for the benchmark.

The draft

Level-up → pool = [upgradeable equipped weapons] + [new weapons if <4 equipped] + [4 stat boosts: +10% dmg, +8% speed, +25 maxHP, +30% pickup] → pick 3 without replacement → apply → resume. Multiple pending levels chain drafts.

Waves & boss

waves.json is a sorted timeline; currentWave() picks the last entry with time ≤ world.time. Spawn timer ticks down by spawnInterval, capped at 350 live enemies. The final wave has "boss": "hive-tyrant" — spawned once via bossSpawned flag; killing it sets victory = true.

XP & gems

  • Enemies drop a gem worth def.xp; tiers by value: common <3, rare 3–4, epic 5–49, legendary ≥50 (different sizes + sprites)
  • Gems inside pickupRadius (90px, upgradeable) magnet toward the player
  • Level curve: xpNext = 6 + (level−1)·5 — linear; extra XP carries over

Survival rules

  • Contact damage → 0.5s invulnerability (sprite flicker via flash) + knockback on the attacker
  • Arena is ±2000px bounded; spawns happen just outside the camera view (spawnRadius adapts to zoom)
  • Run stats tracked live: kills, total damage (→DPS), level, build list — shown on pause/game-over/victory

14 · Likely questions — and the answers

"Why is one draw call better than many?"

Every draw call costs fixed CPU-side driver overhead — validating state and encoding commands. The GPU is fast enough to draw 10k quads instantly; it starves waiting for the CPU to ask. Instancing moves the per-sprite variation into a buffer the GPU reads itself, so CPU cost per frame is constant regardless of sprite count.

"What is instancing, exactly?"

Drawing the same geometry N times in one call. Per-instance attributes (marked with vertexAttribDivisor = 1) advance once per instance instead of per vertex — that's how each quad gets its own position, size, color, UV, flash and rotation.

"Why a texture atlas?"

Texture binds are GPU state changes that break batching. With one atlas, every sprite samples the same bound texture and differs only by UV rect — zero binds inside the frame. Bonus: the same white sprite art is tinted per-instance, so one image serves every color.

"Explain the spatial hash." / "Why not just check all pairs?"

All-pairs is O(n²): 5k enemies → 12.5M checks per tick. The hash buckets entities into a uniform grid, so a query only inspects the cells its circle overlaps — near-constant candidates. Rebuilt every tick in O(n). It's the same idea as a hash map but keyed on grid position.

"What do you mean by object pooling?"

Instead of new/delete per spawn, dead objects go onto a freelist and get re-initialized. Removal uses swap-pop (copy last element over the hole) so arrays stay dense without splicing. Result: no allocation in the 120Hz hot loop → no GC pauses.

"Why a fixed timestep?"

Physics scaled by real frame-time makes gameplay speed depend on the monitor's refresh rate. The accumulator runs sim in fixed 1/120s steps regardless of render rate — 60Hz and 240Hz displays get identical gameplay. The 250ms clamp prevents death-spiraling after a hitch.

"Walk me through bloom."

Render scene to an FBO → bright-pass keeps pixels over a luminance threshold → Gaussian blur them at half resolution (separable: horizontal then vertical passes, ping-ponging between two FBOs) → additively composite over the original. Cheap because separable blur is 2n taps not n², and at half-res it's ¼ the pixels.

"What's an FBO?"

A framebuffer object — a GPU render target backed by a texture instead of the screen. You draw into it like the normal framebuffer, then bind its texture as input to another pass. It's the foundation of all post-processing.

"Why WebGL2 over WebGL1 or Canvas2D?"

WebGL2 gives us instanced drawing (drawArraysInstanced), vertex array objects, and GLSL ES 3.00 — the features the renderer is built on. Canvas2D would push every sprite through the CPU rasterizer; it dies far earlier than even naive WebGL.

"How does enemy AI work?"

Deliberately simple — seek: normalize(player − enemy) × speed × dt, plus a decaying knockback velocity on top. The swarm feel comes from separation (hash-based neighbor push-apart), not from smarter individual AI.

"How is audio done with no files?"

SFX are oscillator frequency-sweeps and filtered noise bursts; music is a setInterval-driven 16-step sequencer layering kick, bass and random arpeggio. A per-name millisecond throttle stops sounds from stacking into clipping.

"What would you do next?"

Meta-progression (persistent unlocks), more stages/characters, texture-array or sprite-sheet animation instead of 2-frame flip, enemy projectiles, and quadtrees if enemy sizes diverged wildly. All explicitly out of scope for this assignment.
